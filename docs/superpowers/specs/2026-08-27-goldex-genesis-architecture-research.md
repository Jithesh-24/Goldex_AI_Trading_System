# GOLDEX — Genesis Architecture Research: Autonomous Gold Trading Intelligence

Research/architecture discovery only. No code. No new phase implementation authorized.

---

## 0. The fact that must govern every conclusion below

Before any architecture discussion: **26 distinct hypotheses have now been tested end-to-end across V4 Phase 3, 3A, and 4** — 7 discovery candidates (rule-based, regime-statistical, linear, tabular-RL, Bayesian-online, HMM, sequence-logistic), 4 representation families (momentum, raw path, multi-scale volatility, volatility-regime-transition), 2 model families (shallow tree, boosted ensemble), 3 new mechanism families (GARCH-family volatility, Kalman-filtered trend, distributional skew/kurtosis/jump), and a direct trajectory-vs-single-snapshot information test. Every single one, when run through a proper chronological out-of-sample check with a shuffled-label null control, came back at or below its own null. Zero for twenty-six.

This is not a reason to abandon the project. It is the single most important input to this document, and Section 18's "actively disprove the architecture" instruction demands it be stated plainly: **any agent architecture proposed below is being proposed with no confirmed evidence that a learnable edge exists in the data it would train on.** An architecture cannot manufacture information that isn't there. If this document recommended a sophisticated agent architecture without saying that, it would itself be the exact failure mode Section 18 asks to be guarded against — a system that *looks* intelligent while its apparent competence is actually zero, because there is nothing yet to be competent about. Every recommendation below is written with that constraint as the load-bearing wall, not a footnote.

---

## 1. What GOLDEX is actually trying to become

Not a model that predicts Gold's next price. A **persistent decision-making system** that observes a continuous market, maintains a belief about current conditions, decides whether an opportunity exists, acts (LONG/SHORT/NO_TRADE), manages an open position through time, exits, and updates itself from the complete experience — repeated indefinitely, one position at a time. This is a sequential-decision / control problem, not a supervised-learning problem, and the entire V3/V4 history above was a supervised-learning problem in disguise (a fresh snapshot, a scalar target, one prediction). The mandate's own framing (Section 3: "observation → internal state → interpretation → hypothesis → action → consequence → experience → updated internal state") is the correct problem statement; V3/V4 never actually built or tested that loop.

## 2. Why V3/V4 failed to answer that problem

They didn't fail to find an edge because the wrong model was chosen — they never tested the actual problem. Every V3/V4 candidate answered "given this snapshot, predict this scalar," which is a different, easier, and less relevant question than "given the current situation and my open position, what should I do now." Phase 3A's own report explicitly flagged trajectory-level learning as "untested, not ruled out," and Phase 4's Stage 1 tested it directly — the one clean trajectory-vs-snapshot experiment built specifically to answer this — and it, too, came back null (0.529 vs 0.529 accuracy, both barely above a 0.500 null, n=18,405 real trajectories). So the honest statement is stronger than "V3/V4 asked the wrong question" — it is "V3/V4 asked the wrong question, and when Phase 4 finally asked something closer to the right one, on the same data, it still found nothing." That is real evidence about this data source, not a methodology gap.

## 3. What assumptions from V3/V4 should be discarded

- That a bigger model, more features, or one more mechanism family will find what smaller ones didn't — 26 hypotheses across increasing sophistication (rule → tabular RL → HMM → tree → boosted ensemble → GARCH/Kalman) show no trend toward "getting warmer."
- That M1-resolution, single-instrument (Gold-only), 6.7-year historical price data necessarily contains a discoverable short-horizon edge at all — this has not been established, and continuing to assume it while changing only the model class is the exact "another version of the loop" Section 13 warns against.
- That the fix is architectural sophistication rather than a fundamentally different evidence source (finer resolution, a different market regime characterization, or accepting a longer/different horizon than 5 bars).

## 4. What infrastructure should be retained

Everything genuinely reusable and untouched by the negative results: Phase 1's leakage-proof simulator (`simulator/`), Phase 2's control-gate/CI-verdict/EV-cost machinery, Phase 3's `learn()` hook, Phase 3A's `observation_features` recording, Phase 4's `decision_id` trajectory linkage and trajectory-assembly module. None of this is what failed — the *hypotheses tested through it* failed. This is a critical distinction: the laboratory is sound; what's been grown in it hasn't worked yet. Any genesis architecture should sit on top of this infrastructure, not replace it.

## 6. Quantitative knowledge-library architecture

Per Phase 4's design (already approved) and this document's Section 5 conclusion: mechanisms remain **evidence sources feeding a gate**, never votes, never hardcoded rules, never strategies with permanent priority. The library from the mandate's Section 4 is legitimate as a *menu*, not a commitment — but Section 0's evidence means the menu should be evaluated one item at a time with the same cheap-test-first discipline already proven (Phase 3A/4's MI-vs-null → OOS-check pattern), not implemented wholesale. Two families explicitly flagged by the mandate deserve direct comment:
- **Black-Scholes / options math**: unchanged verdict from the Phase 4 design — no legitimate direct role for spot XAUUSD without options data GOLDEX doesn't have; GARCH/stochastic-volatility remain the correct substitute and were already tested (null, Section 0).
- **Optimal stopping theory** (new to this document, per external research): a legitimate, mathematically mature framework specifically for the exit-timing problem, with a caveat — classical results assume mean-reverting (Ornstein-Uhlenbeck) dynamics, and GOLDEX's own Phase 3 finding (weak 1-bar return autocorrelation, no confirmed mean-reversion) means this framework's assumptions are not yet validated for gold at this resolution either. It should be tested, not assumed.

## 7. How the agent should "see" the market

Translate "seeing the market" technically as: a **persistent, updated-every-bar belief state** built from (a) the raw representation layer (price, spread, volume — already exists), (b) whichever quantitative mechanisms pass their own cheap validation (Section 6), (c) the agent's own recent action/outcome history (already recordable via Phase 4's `decision_id`/trajectory infrastructure), and (d) account state (Section 10). This is Phase 4's design doc's Market State Layer, unchanged — Section 0's results don't invalidate the *architecture* for representing state, they invalidate specific *mechanism* claims that have been tested. Whether M1 is fundamentally insufficient for this: **not established either way yet**, because nothing tested so far isolated resolution as the variable — every negative result used M1 features (raw or engineered) at M1 resolution. The honest position is the same as Phase 4's design doc: tick data becomes justified only when a specific mechanism is shown to need it, and no such case has been made. Do not acquire tick data as a blanket fix for 26 negative results whose common factor could equally be "no edge at this horizon on this instrument" as "wrong resolution."

## 8. How the agent should learn from historical experience (the simulation-as-learning-world question)

The existing simulator already satisfies most of Section 7's requirements: chronological causality (Phase 1's dedicated no-look-ahead test), realistic costs (Phase 1/2's spread/slippage/liquidation modeling), and now (Phase 4) trajectory-level experience capture. What it does **not** yet have, and would need before any agent training beyond a single-pass supervised combiner: (a) a formal repeated-exposure protocol — training an agent by replaying the same 6.7 years multiple times risks memorizing the exact historical path rather than learning generalizable structure, which needs to be guarded against explicitly (e.g., via held-out sub-periods used as pseudo-OOS during development, distinct from the real final OOS boundary, which stays untouched); (b) an explicit reward-hacking audit process for anything beyond the current CI-gate evaluation, since a persistent agent has far more surface for exploiting simulator quirks than a single-shot classifier does. Per the mandate's Section 7, training/validation/OOS for an autonomous agent needs the *same three-way split* Phase 1-4 already use, just with the addition that the training partition itself needs internal held-out slices for iterative agent development (the same pattern Phase 3A/4 already used for their internal 240k/60k splits) so the real OOS boundary is touched exactly once, at the end, regardless of how many training epochs/episodes the agent goes through internally.

## 9. How the agent should learn from its own trades

Not "update after every profitable trade" (mandate Section 8 correctly flags this as wrong). The correct objects to learn from, mapped to what the trajectory infrastructure already captures: a profitable trade updates whatever produced the *entry* decision positively, credited to the actual state at entry (Phase 3's credit-assignment bug — fixed in review — is the cautionary tale here: get this wrong and every result downstream is meaningless); a losing trade needs the same precise credit, not blanket discouragement of the acting mechanism, since even a good decision loses sometimes; an early exit's correctness can only be judged against the counterfactual "what would have happened if held" — expensive to compute honestly, and a real design problem, not a solved one; a missed opportunity (NO_TRADE that would have won) is the hardest of these to learn from without inducing overtrading bias, and should be approached cautiously if at all; execution-cost events should feed the EV-gate (already exists, Phase 2) rather than a separate learning signal. **Credit assignment is the single hardest unsolved piece of this whole section** — harder than architecture choice — and deserves its own small, dedicated research pass before any agent training is attempted, not an assumption that "the trajectory data now exists so credit assignment is solved."

## 10. How strategy discovery should work

Per Section 14's explicit question (predefined vs. learned vs. hybrid): **hybrid, with the predefined half kept deliberately small and evidence-gated.** Pure learned-representation-discovery (no prior knowledge at all) is the most sample-hungry option and least justified given 6.7 years of 1-minute data is not large by deep-learning standards; pure predefined-library selection is exactly the strategy-zoo pattern already shown not to work standalone (Architecture A, Section 5). The hybrid the mandate's own Section 3 gestures at — mechanisms as *optional evidence*, with a learned combiner deciding relevance — is the correct middle ground, but Section 0 means "the mechanisms tried so far are optional evidence that hasn't yet been evidence of anything real," so the discovery process must keep testing new mechanism candidates cheaply (Phase 3A/4's pattern) rather than assuming the current menu is sufficient just because it's broad.

## 11. How expert disagreement should be handled

Under Architecture B (gated MoE): disagreement is a *feature* the gate should be trained to recognize, not a bug to average away. A gate that has learned "when mechanism A and mechanism B disagree, historically neither was reliable, so abstain" is exactly the mandate's Section 3 "when no mechanism is trustworthy" requirement, implemented mechanically via low combined gate confidence feeding directly into the EV-gate's NO_TRADE default. This requires the combiner to output a real, calibrated confidence (not an arbitrary softmax number) — external research already flagged (Phase 4 design doc) that ML confidence is commonly miscalibrated, so this needs explicit calibration validation before being trusted for abstention decisions, not assumed.

## 12. How market state should be represented

Persistent, updated every bar (not recomputed from scratch), built from mechanism outputs + recent action/outcome history + account state (Section 7). Latent (learned) vs. explicit (hand-labeled regime) representation: per the mandate's Section 3, do not hardcode "this is a trend"/"this is regime 3" unless evidence justifies it — and no evidence yet does. Start with the state layer as a concatenation of validated mechanism outputs (interpretable, auditable) rather than jumping to a learned embedding, both because interpretability matters more than usual right now (every result needs careful interrogation per Section 0) and because a learned embedding needs more data/training signal to justify than a concatenation of already-tested scalars.

## 13. How entry/exit/SL/TP/sizing should be learned

Per Section 9 of the mandate and Section 5/6 of this document: these are **not one problem**. Entry (whether/direction) is the gated-MoE combiner's job. Exit is a genuinely different problem, best framed through optimal-stopping theory (Section 6) as a first hypothesis, tested the same cheap-first way as everything else — not assumed to need the same architecture as entry. SL/TP: the mandate correctly says the agent shouldn't be forced to wait for a fixed TP, but this doesn't mean SL/TP have no role — they remain a scientifically legitimate *safety-net* function (Phase 1's simulator already enforces this) even if the primary exit decision becomes dynamic. Sizing: deferred until an entry/exit decision has any validated signal at all — sizing a decision that isn't yet known to be right is optimizing decoration, not substance.

## 14. How account awareness should work

Unchanged from the Phase 4 design's Section 11: account state (balance, equity, drawdown, exposure) informs risk gating but must be kept architecturally separate from the training signal that shapes the entry/exit decision itself — the combiner should never see "I'm down money" as an input that changes what it believes about the market, only as an input to a downstream, separate risk/sizing layer. This is the concrete mechanism that prevents the martingale/loss-chasing failure mode the mandate explicitly rules out, rather than hoping training data alone discourages it.

## 15. Data requirements

6.7 years of M1 data has now been tested against 26 hypotheses spanning 4 representation families, several model families, and one trajectory-level test, with zero surviving OOS. This does not prove the data is insufficient — it's consistent with either "insufficient data/resolution" or "no edge exists in Gold at this horizon regardless of data" or "the right combiner/state-representation hasn't been tried yet." Per Section 15 of the mandate: do not conclude "more data is better" reflexively. What would materially change the problem: (a) tick-level bid/ask data, which addresses microstructure information M1 structurally cannot represent (genuinely different information, not just more of the same) — justified specifically if a mechanism needing it is identified, not as a blanket fix; (b) a longer or different horizon than the 5-bar target used in every experiment so far — this has never been varied, and is a cheap, high-value thing to test before acquiring any new data source at all; (c) additional correlated instruments (e.g., DXY, real yields, other metals) as *context* features rather than a different resolution of the same instrument — untested, cheap to add to the mechanism menu.

## 16. Compute requirements

Architecture B (gated MoE over a handful of validated mechanisms) is cheap — comparable to Phase 3/3A/4's existing per-experiment cost (hours, CPU-bound). Architecture E (full RL) would require materially more compute and, per external research, RL is notoriously sample-inefficient — 6.7 years of 1-minute bars (~3.5M rows) is not large by RL-training standards, which is itself an argument against jumping to E without evidence, independent of the compute cost. Recommendation: stay on the cheap end of the ladder until evidence, not budget, forces an escalation — this matches the project's already-established discipline (Phase 3A/4's "compute cost is an engineering constraint, not evidence of unsuitability, but also not a reason to skip cheap tests first").

## 17. Live architecture requirements

Deferred in detail (this is Phase 6+ scope per the existing roadmap) but the one requirement this document adds: whatever state-layer/mechanism/gate architecture gets built must be computable identically from a live MT5 feed as from historical replay — already an existing invariant (`MarketState`'s `source` field distinguishes `synthetic_replay` from `mt5_live`) and must not be broken by whatever gets built next. Do not claim millisecond-precision execution without measuring actual MT5 API/broker latency first — no such measurement exists yet in this project, and claiming a latency requirement the architecture hasn't been shown to meet would itself be the "sophisticated backtest that looks intelligent" failure mode extended into deployment claims.

## 18. Main failure modes

- **The Section 0 problem generalized**: any agent architecture, however well-designed, can appear to work in-sample or even on a naive OOS split while having learned nothing generalizable — this is the single largest risk given 26 prior negative results already needed careful null-control scrutiny to interpret correctly.
- **Gating collapse** (Architecture B, documented in general MoE literature): one mechanism dominates the gate, degenerating into Architecture A with extra steps.
- **Reward hacking / simulator exploitation**: a persistent agent has far more surface to find simulator quirks than any single-shot Phase 1-4 candidate did — this risk scales with agent sophistication, another reason not to jump straight to full RL.
- **Credit-assignment errors**: Phase 3's real, review-caught bug (crediting the wrong trade to the wrong internal state) is a preview of a much harder version of the same problem at agent scale (Section 9) — this is not hypothetical, it already happened once at a smaller scale.
- **Live/sim divergence**: nothing in this project has yet measured live MT5 latency or live spread/slippage behavior against the simulator's model of it — a real, currently-unquantified gap.

## 19. Anti-overfitting design

Extend, don't replace, what's already proven: chronological-only splits, shuffled-label null controls on every new statistical claim (already standard practice, Phase 3A/4), the untouched final OOS boundary touched exactly once, explicit multiple-testing tracking (the ledger now at 26 entries and growing — Phase 4's report already does this and it should continue), and per Section 17's external research, Combinatorial Purged Cross-Validation (CPCV) as an upgrade over simple walk-forward for any future agent-level validation, since CPCV is documented to produce a lower Probability of Backtest Overfitting and higher Deflated Sharpe than the walk-forward approach used so far. For an agent specifically (not just a single-shot model): repeated-exposure-to-history risk (Section 8) needs its own explicit safeguard — internal held-out sub-periods distinct from the real OOS boundary.

## 20. Architecture comparison matrix

See Section 5's table — repeated here as the single source of truth for the comparison the mandate asked for. Summary ranking for "what to build first, given Section 0's evidence": **F (contextual bandit, entry-timing-only) and B (gated MoE, opportunity-detection) tie for cheapest-and-most-justified next step; optimal stopping (Section 6/9) for exit specifically; C, D, E all deferred pending evidence from B/F.**

## 21. Recommended architecture

**A gated mixture-of-experts over a small, evidence-validated mechanism set, for the entry/opportunity-detection decision specifically, with exit handled as a separate optimal-stopping-theory research track, and account-aware risk sizing kept architecturally downstream of both — not a single unified agent, and explicitly not full RL, a world-model, or a monolithic learned-representation system at this stage.** This is a direct, reasoned rejection of collapsing the whole OBSERVE→...→LEARN loop into one architecture: the entry and exit problems have different mathematical structures and different literatures, and forcing them through one mechanism (whether that's "vote among strategies" or "one big RL policy") has no evidentiary support and real documented failure modes on the RL side specifically.

## 22. Why the alternatives were rejected

- **A (voting)**: already tested in spirit (Phase 3's roster) and shown insufficient without a learned combiner.
- **C/D (learned state + experts, unified/joint)**: not rejected outright, but deferred — no evidence yet that static per-mechanism conditioning (B) is exhausted, so building a more complex, less interpretable successor now would be escalating without justification, the exact anti-pattern Section 17 of the mandate warns against ("do not reject advanced methods merely because they are expensive... but do not recommend enormous architectures without evidence").
- **E (full RL / world models)**: rejected for now specifically because (a) the one direct multi-step-structure test built (trajectory-vs-snapshot) came back null, removing the strongest available justification for needing multi-step credit assignment; (b) RL's documented failure modes (reward hacking, sim-to-real gap, sample inefficiency) are severe and well-evidenced externally; (c) no public precedent was found (external research, Section 3 of this doc) for world-model/Dreamer-style approaches in trading at all — this would be genuinely unexplored territory, appropriate only after cheaper approaches are exhausted with actual positive evidence to build on, not as a first move.

## 23. What must be proven before implementation

1. That at least one mechanism from the Section 6 menu, or a genuinely new representation (a different horizon, Section 15b), beats null OOS — nothing currently does, and this is a hard precondition, not a nice-to-have.
2. That a gate conditioned on multiple mechanisms' joint state does better than any single mechanism alone — untested; this is the actual claim Architecture B rests on, distinct from "does mechanism X work alone" (already tested, repeatedly, negatively).
3. That credit assignment for a persistent agent (Section 9) can be implemented correctly — needs its own dedicated correctness proof (unit-tested, review-verified) before any training run, given Phase 3's precedent bug.

## 24. The smallest credible first experiment

Not a new mechanism (26 have been tried; diminishing returns on "one more feature" is itself now evidence). The smallest credible next step is: **vary the prediction/decision horizon.** Every experiment across Phase 3/3A/4 used a 5-bar forward-return target — this single choice has never been tested as a variable. A cheap MI-vs-null sweep across several horizons (e.g., 1, 5, 15, 30, 60 bars) using the existing, validated methodology (Phase 3A/4's estimator, reused verbatim) would answer a genuinely new question with near-zero new infrastructure, and directly informs whether GOLDEX's short-horizon/scalping ambition (mandate Section 1) is even the right timescale to be searching at, before any gate/combiner/agent architecture is built around an assumed horizon.

## 25. Proposed roadmap (historical learning → demo → live)

1. **Horizon sweep** (Section 24) — cheap, answers whether 5 bars specifically was the wrong target all along.
2. **If any horizon shows real OOS signal**: build the smallest gated-MoE combiner over the mechanisms that individually correlate with that horizon, evidence-gated at every step (same discipline as Phase 3A/4).
3. **If a combiner shows real signal**: begin the exit-specific optimal-stopping research track in parallel, since entry and exit are separable problems (Section 13).
4. **Only if both entry and exit show validated signal**: consider RL/sequential architectures for anything the combiner+stopping-rule combination genuinely can't handle — not before.
5. **Phase 5-equivalent validation**: full untouched-OOS test of whatever survives, using CPCV-style validation (Section 19) rather than simple walk-forward.
6. **Phase 6-equivalent**: XM demo, with live-vs-simulator latency/spread/slippage reconciliation measured explicitly before any claim about live viability is made (Section 17).
7. **Live, real-money**: only after demo-period performance matches simulator expectations within a pre-specified tolerance, decided before the demo period starts, not after seeing results.

If step 1 shows nothing at any horizon, the honest, evidence-supported conclusion is that M1-resolution single-instrument Gold price/volume/spread data does not contain a learnable short-horizon opportunity-capture edge discoverable by the methods available to this project, and the next real decision is about data (tick, cross-instrument, options) or scope (a different asset, a different horizon regime), not about architecture — no agent design, however sophisticated, fixes an absence of information.
